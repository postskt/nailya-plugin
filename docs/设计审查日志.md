- **问题分级**：🔴 P0（影响核心功能/正确性）｜🟡 P1（明显缺陷，建议修）｜⚪ P2（冗余/打磨项）

## 一、不必要的设计（死代码与冗余）

### 1.1 🔴 整个"语境雷达"选图引擎是死代码（约 150 行）
- **位置**：`analyzeDialogueContext`（L2004-2092）、`getBriefCnLabels`（L2095-2155）、`hashStringSeed`（L1966-1974）、启动期的 `COMPILED_CAT_REGEX` 预编译循环（L676-713，遍历 600+ 个关键词构建正则）。
- **问题**：`analyzeDialogueContext` 和 `getBriefCnLabels` 在全文件中**没有任何调用点**。display handler 的 `<Vis:` 处理走的是另一套 `findBestImageForVisTag`（直接拿 AI 报的中文标签字符串做 `includes` 匹配）。`COMPILED_CAT_REGEX` 只被死函数消费，等于每次启动白做一遍 600 多个关键词的正则编译。
- **影响**：白耗启动时间和体积；`BASE_TAG_DICT`（约 90 行、近 2000 个词条）本身还在被 `parseImageStructure` 的文件名解析使用，但"按对话内容自动选图"这条设计路线实际已经废弃。
- **建议**：要么删除 `analyzeDialogueContext`/`getBriefCnLabels`/`hashStringSeed`，恢复"文件名解析 + AI 报标签"两条腿走路；要么把 `<Vis:` 选图改回语境雷达驱动。二选一，不要养着一套不跑的引擎。

### 1.2 🔴 `maxCandidateCount` 是死配置，且 UI 文案与实现不符
- **位置**：配置项（L137"从原42张缩减至16张，大幅削减Token"）、资产页可编辑按钮（L3878-3888，提示"设置单次注入给 AI 的候选图片上限"）。
- **问题**：全文件搜索不到该值在注入/请求路径上的任何消费者——当前实现是"让 AI 输出 `<Vis:` 标签、本地选图"，**从不把候选图片列表发给 AI**。注释里"从 42 缩减到 16 省 Token"的优化对象并不存在。
- **影响**：用户按 UI 文案调整候选池数字不会有任何实际效果，属于功能性欺骗。
- **建议**：删除该配置与 UI 按钮；或真正实现"候选图片清单注入"并让该值生效。

### 1.3 ⚪ 图标系统三套方案只留了一套"反选"
- **位置**：`ICON_MODE`（L14）固定为 `'html-emoji'`，但下方精心绘制的渐变 SVG 图标、`btoa` 转 data URL、三种 fallback 分支（L17-56）全部成为永远走不到的代码；注释还写着"推荐 img-svg（绕过DOMPurify完美呈现）"。
- **建议**：定死一种图标方案，删掉其余两套和模式开关。

### 1.4 ⚪ 脏标记增量存储名存实亡
- **位置**：`markDirty`/`saveStoredData`（L150-262）。
- **问题**：设计初衷是"只序列化变化的表"，但①无参 `markDirty()` 直接把四张表全标脏（与全量保存无异）；②实际业务代码几乎全部走 `saveStoredData(true, ['profiles','aiCache'])` 显式传 key，dirty 集合机制基本被绕开；③`immediate` 与 180ms debounce 两条路径并存，`dirtyStoreKeys.clear()` 在 `await Promise.all` 之前执行，immediate 调用与 pending timer 交错时有重复写/漏写窗口。
- **建议**：统一为"调用方显式传 key"一种模式，删掉 dirty 集合这套第二机制。

### 1.5 ⚪ 双重删除控制标签
- **位置**：output handler（`handleAiOutputAndMilestones` L2425-2515 已做建档+删除）与 display handler（L4093-4097 又做一遍同样的三个 replace）。
- **问题**：`<AI档案解析>` 在 output 阶段已建档并删除，display 再删只是防御重放历史消息；两处正则完全重复。
- **建议**：display 里保留删除可以，但应抽成公共函数；且要意识到历史消息重渲染时 display 不会再触发建档——两处行为其实不一致，重复只是巧合掩盖。

### 1.6 ⚪ 其它零碎冗余
- `stVars` 酒馆宏变量（L124）：仅存内存、每次请求重建、不持久化，`{{setvar}}/{{getvar}}` 跨轮根本传不了值——机制上是摆设。
- `runtimeCache.turnCounter`（L176）从未被读取。
- `buildOutfitAndBodyPromptBlock(prof, tag, sceneCtx)` 的 `sceneCtx` 参数（L2220、L2561 传 `{contextSeed:1}` 占位）没有消费者。
- 版本号 `"5.5.8"` / `V5.5.8` 硬编码在按钮名、日志前缀、备份 payload、UI 标题等约 20 处，没有版本常量。
- `FAVOR_BEHAVIOR`（L411-417）与 `getFavorStage` 的 `desc`（L404-408）是两份语义重复的档位描述。
- 备份页每次渲染都把全量 JSON（可能几百 KB）塞进 textarea（L4006），纯展示开销。

## 二、设计不足（缺失与薄弱环节）

### 2.1 🔴 原生 `prompt()/alert()/confirm()` 在插件 iframe 中很可能被禁用
- **位置**：手动建档（L3037）、图包绑定（L3553）、好感/年龄编辑（L3596）、生理编辑（L3623）、预设导入/编辑（L3726-3741、L3816）、备份恢复入口判断等，共约 15 处核心交互全部依赖原生弹窗。
- **问题**：插件运行在沙箱 iframe 中，宿主若未给 iframe 加 `allow-modals`，`prompt/confirm/alert` 会**静默返回 null/false**——用户点"手动建档""编辑好感""绑定图包"将毫无反应，且无任何报错。官方文档推荐的 UI 路径是 iframe 内自建 DOM（插件自己明明有完整的 modal 组件却只用于穿搭编辑）。
- **建议**：全部交互迁到自建 modal（已有 `wardrobe-modal` 可复用模式），或至少做一次能力探测降级。

### 2.2 🔴 主模型"搭车建档"机制不可靠且会永久卡死
- **位置**：`buildAiAnalysisPrompt(forMainModelPiggyback)`（L1301-1307）、注入（L2583-2586）、回收（L2425-2444）。
- **问题**：
  1. 要求主模型在**正常 RP 正文之后**追加一个巨大的 `<AI档案解析>` JSON——输出长、格式要求高，极易被截断或遗忘；一次性消耗大量 token，用户毫无感知。
  2. 只有解析成功才 `pendingMainModelExtract.delete(ctx.key)`（L2436）；模型一旦没输出标签，pending 永不释放也**不再重试注入**——该卡从此既不能自动建档、也没有任何提示，只能手动走独立 API。
  3. 该 JSON 解析失败时只写 console，用户侧完全静默。
- **建议**：失败 N 次后放弃并 toast 提示；改为独立小请求（如让模型在下一轮只输出 JSON 且限制 max_tokens），或干脆引导用户填 key。

### 2.3 🔴 好感度双轨制互相打架
- **位置**：`calculateFavorGain`（L2281-2301，插件按关键词+随机数自动加减）vs 好感度墙机制（L419-434，要求 AI 在剧情到位时上报 `<好感度事件>`）。
- **问题**：分数由插件本地随机涨（2~6 + 关键词加成），而"告白墙/婚姻墙"的触发说明又写进 System Note 让 AI 判断"分数到达 50 必定主动告白"。但 AI 看到的分数和插件实际推进节奏完全脱节：AI 认为该告白了，分数可能还没到 50（墙锁定）；或者分数到了 AI 却不配合输出事件标签。另外关键词匹配极其粗糙：负向判定 `/(?:扇|打|踹|骂|…)/` 中"打"会命中"打电话/打伞"，"夸"单字、"礼物"等正向词误判率高。
- **建议**：要么分数也交给 AI 事件上报（插件只做钳制），要么把关键词评分做得更严格（分词+否定检测）。当前两套机制混跑必然出现行为矛盾。

### 2.4 🟡 受孕判定逻辑自相矛盾
- **位置**：`updatePhysiology`（L2303-2353）。
- **问题**：`pregnancyRisk` 在任何性爱日累积（排卵期 30% × 避孕系数），但**只有 cycleDay==24 当天掷骰判定一次**；24 天之后累积的风险永远不会结算，而 28 天周期翻转时 risk 清零（L2349）。即"第 25 天内射"累积的风险毫无意义。另外"无套"不在 `PROTECT` 关键词表中，`/裸/` 会误匹配"裸辞"。
- **建议**：把判定改为"每次新增风险后即掷骰"或"周期结束时统一结算"；补齐"无套"词条并去掉裸字面匹配。

### 2.5 🟡 改名会产生档案分叉（槽位键含名字）
- **位置**：槽位键 `slotOf = chatId + '#' + 名字`（L547）；穿搭编辑弹窗保存（L3331-3357）允许改名但不更新 slotKey；AI 建档 `applyAiAnalysisResultToChat` 按 `slotOf(chatIndex, cnName)` 新键写入（L1372）。
- **问题**：改名后同一角色出现"旧名槽"与"新名槽"两份档案，好感/生理进度分叉；UI"全部档案"页会看到重复角色。AI 重识别时删除旧槽的匹配条件（L1354-1359）里有一条 `/[\uac00-\ud7a3]/.test(oldProf?.name)`——**只要旧名是韩文就无条件匹配任意新角色**，多女主卡会删错人的槽。
- **建议**：槽位键改用稳定 ID（assetPrefix 或建档时生成的 uuid），名字只作显示；韩文兜底匹配必须限定在 `matchedNew` 匹配成功的前提下。

### 2.6 🟡 酒馆预设接管丢弃了 RisuAI 的上下文管理
- **位置**：`buildMessagesWithSillyTavernPreset`（L1878-1961）、replacer（L4145-4166）。
- **问题**：接管后消息数组完全由插件重组，但插件**没有任何 maxContext/token 预算裁剪**——长对话会原样全量发送，直接爆上下文。`chatHistory` 过滤只认 `startsWith('[System Note')`（L1887），对宿主消息结构的兼容极其脆弱；未支持 `injection_position` 的 relative 排序细节、未合并相邻 system 消息（部分 API 对散落 system 敏感）。世界书激活启发式（`position===0 || insertorder<50`，L1867）与酒馆真实语义不符。
- **建议**：接管前至少做一轮 token 估算与历史裁剪；在 UI 明示"接管后上下文长度管理由本插件负责"。

### 2.7 🟡 System Note 全部堆在消息末尾
- **位置**：L4161-4165（非接管路径 `messages` 尾部追加全部角色 note）；接管路径同样 push 到 `finalMessages` 末尾（L1954-1958）。
- **问题**：多女主卡时每个角色一整段 note（档位行为+两道墙+穿搭铁律+视觉指令，单角色 600+ 字）全部 system role 挂尾，token 膨胀严重且对补全类 API 的遵从度差；没有深度注入选项，也没有按"本轮被提及角色"过滤（好感计算里有 mentionedProfiles 逻辑，注入侧却没有复用）。
- **建议**：复用 mentionedProfiles 过滤注入对象；提供深度注入；精简 note 模板中的重复话术。

### 2.8 🟡 15 秒超时对"全卡分析"过短
- **位置**：`runIndependentAiAnalysis`（L1464）与 `runTargetedAiSupplement`（L1610）共用 15s 熔断。
- **问题**：全卡分析的 prompt 包含最多 9500 字符描述 + 18000 字符世界书，输出是十几个角色的完整档案 JSON——15 秒内完成对多数模型不现实（尤其推理模型），必然频繁超时，而 UI 提示却让用户"检查网络或更换节点"，误导排障方向。
- **建议**：按任务类型区分超时（补录 30s / 全卡 120s+），并显示已等待时长。

### 2.9 🟡 `<好感度事件>` 解析无容错
- **位置**：L2487 直接 `JSON.parse(m[1])`。
- **问题**：同一文件里明明有成熟的 `extractJsonFromAiResponse`（剥离代码块/首尾花括号），这里却裸 parse——模型多输出一个换行注释整个事件就静默丢弃（外层 catch 吞掉）。
- **建议**：统一走 `extractJsonFromAiResponse`。

### 2.10 🟡 去重签名脆弱
- **位置**：`handleMessagePipeline` 的 sig（L2360）：`秒级时间戳 + 前40字符`。
- **问题**：同一秒内连续发送且前 40 字相同的两条不同输入，第二条被静默吞掉（好感/时间不推进）；相反跨秒的重复消息会重复处理。
- **建议**：与宿主消息队列的真实 message id/索引挂钩，或用完整文本哈希。

### 2.11 ⚪ UI 未对用户输入做 HTML 转义
- **位置**：`createProfileCardNode` / `openWardrobeModal` / 索引徽章等大量 `innerHTML` 模板直接插 `prof.name`、`w.top` 等用户可控值（如 L3443、L3256）。
- **问题**：角色名含 `<`、`"` 时破版式；虽在插件自身 iframe 内、XSS 风险有限，但名字来自 AI 输出/卡文件，属于不可信输入。
- **建议**：加一个 3 行的 `esc()` 工具函数统一转义。

### 2.12 ⚪ 数据体量与存储选型隐患
- **位置**：`pluginStorage`（存档级、跨设备同步）承载全角色档案 + 全部卡 AI 缓存 + 全部酒馆预设，整体 `JSON.stringify` 单键写入（L237-246）。
- **问题**：①换存档即"数据全丢"，与"全卡档案库"的产品定位不符，UI 中也无任何说明；②数据含 API Key 明文，且**全量备份 JSON 会原样带出 Key**（`exportFullBackupJson` L298-309 无脱敏），复制/下载分享即泄露；③缓存无上限、无 LRU，多卡重度使用后单键写入越来越慢。
- **建议**：备份导出时脱敏 Key（导入已有保留逻辑，导出也应对称处理）；考虑按卡分键存储；文档说明 pluginStorage 作用域。

### 2.13 ⚪ `<Vis:` 选图失败静默吞标签
- **位置**：display handler L4110，`findBestImageForVisTag` 返回 null 时标签直接替换为空串。
- **问题**：用户看到 AI 明明输出了分镜意图但没图、没提示，无法分辨是"卡里没这张图"还是"前缀绑定错了"。
- **建议**：失败时替换为可见的占位提示（如 `[未找到立绘: xxx]`），至少 console 记录原因。

### 2.14 ⚪ Handler 重复注册风险未验证
- **位置**：`addRisuScriptHandler`/`addRisuReplacer`（L4066-4169）；`onUnload` 只清理了 UI parts（L112-116）。
- **问题**：官方文档仅明确 TTS hook 会自动清理；若宿主对 script handler/replacer 不做自动回收，插件热重载/反复启用会导致 handler 叠加——好感度被加两次、System Note 注入两份。至少应在 onUnload 里显式调用对应的 remove API（若存在）并在日志中验证。

## 三、不合理的设计

### 3.1 🔴 好感度墙的"锁定"实现依赖注入文本吓唬模型
- **位置**：`FAVOR_WALLS.note`（L419-434）+ 注入钳制（L2409-2411：`if (!confirmed && favor > at) favor = at`）。
- **问题**："正向变动记 0，不得越过"并没有真正实现——插件侧仍会随机加分然后被钳回 50，模型侧全靠 System Note 里的一段话约束。模型不配合时表现为：剧情早已该告白，但 UI 分数卡死、AI 每轮被告知"她明显但说不出口的犹豫"，与剧情脱节；反之模型单方面输出 `<好感度事件>` 确认即可跳墙，**没有任何使用者确认校验**（note 里说"必须等使用者明确接受"，但代码只信 AI 的 JSON，用户在 UI 手动确认按钮只是另一个入口）。设计宣称的硬约束实际是软提示。
- **建议**：要么把确认权收回插件（检测到墙到期先暂停加分并弹 UI 询问用户），要么承认是软引导、删掉"必定/硬性"级别的措辞。

### 3.2 🟡 时间推进三轨制互相踩
- **位置**：用户输入正则（L2257-2279）+ AI 正文正则（L2455，只扫前 400 字符）+ AI 标签 `<时间推进>`（L2447-2453）。
- **问题**：①AI 正文正则匹配"第二天/次日"等短语极易误触发（"第二天再说""明天又是新的一天"类修辞），剧情里随口一句就跳一天、推动生理周期；②依赖 `lastUserInputAddedDays` 全局变量在 input/output 之间传递守卫，若本轮 output 未触发（生成中止、报错），残留状态会污染下一轮；③每月固定 30 天的简化历法与 AI 叙事的"大月/日期"表达冲突。
- **建议**：只保留 `<时间推进>` 标签单轨，正文正则至少要求"过去式推进"上下文（如"次日清晨"且后接叙事）。

### 3.3 🟡 注入的 System Note 与 RisuAI 预设/酒馆预设三方叠加时职责不清
- **位置**：replacer L4145-4166。
- **问题**：酒馆接管开启时，插件的 systemNotes 追加在酒馆预设重组后的消息数组末尾——酒馆预设作者精心安排的层级被一个不明 system 戳穿；关闭时又追加在 RisuAI 原生消息后面。三套预设系统（RisuAI 原生 / 酒馆接管 / 插件 note）的优先级与共存策略从未向用户说明，出问题时无法归因。
- **建议**：在 UI 中明确三方关系，并让 note 支持选择注入位置（头/尾/深度）。

### 3.4 🟡 思维链折叠产物依赖宿主渲染管线放行
- **位置**：display handler L4131-4134，把 `<thinking>` 替换成带内联 style 的 `<details>` HTML。
- **问题**：RisuAI 的消息渲染会经过自身的 sanitize/格式化，内联长 style 的 `<details>` 能否原样呈现取决于宿主行为，插件等于在赌渲染器放行；`foldThinkingBlock` 开关又被放在"酒馆预设"标签页下（L3700），而它是纯显示层功能，与预设无关。
- **建议**：功能入口移到通用设置；实现上优先用宿主提供的格式化机制而非硬塞 HTML。

### 3.5 🟡 `age >= 14` 才启用生理演算的魔法数
- **位置**：L2413、L2471。
- **问题**：14 这个阈值无出处、无注释、无 UI 暴露；低于 14 的角色档案照样建档并注入"年龄: N"与好感档位行为，只是跳过生理部分——阈值语义（保护？还是省 token？）模糊，属于内容安全敏感区却做得最随意。
- **建议**：明确该阈值含义；如出于内容安全考虑，应同样约束行为基线注入而非只跳过生理。

### 3.6 ⚪ `profilesOfChat` 在读路径里做写迁移

### 2026-10-31 V6.1.0 修复⑤：AI 从不输出 `<Vis:` 标签的诊断与加固（用户报告"图片凭空出现且对不上剧情"）

**诊断结论**：用户看到的"文末凭空出现的图"是**语境雷达兜底**在出图（无标签、粗匹配、必不对装），而 Vis 主链路从未启动——说明注入的视觉指令从未到达 AI。结合"重装/换模型/换卡均无效"，最大嫌疑为 **replacer 注入权限被拒绝过一次且被宿主按插件内部名（favor_physio_manager）持久记忆**。

**加固措施**（V6.1.0 上实施，54/54 断言通过）：
1. **注入状态灯**：初始化时捕获 `requestPluginPermission('replacer')` 结果存入 `runtimeCache.injectionDenied`，被拒时启动弹长警告；插件面板头部新增「注入:✓正常/⛔未授权」按钮，点击可重新申请权限。
2. **视觉强制令上顶部**：topNote（对话最顶端）追加"视觉标签强制令·最高优先级"——含格式、示例、三槽位中文必填、多角色逐个输出要求。顶部位置遵从度远高于尾部说明书。
3. **备用注入通道**：`injectionDenied` 期间，input handler 在用户输入末尾附加一行视觉指令随消息发给 AI（有轻微聊天污染，仅权限被拒时启用）。
4. **注入预览**：「图包与索引」页新增「注入预览」按钮，弹窗展示实际发给 AI 的顶部时间+强制令与尾部说明书原文（聊天窗口内不可见，借此肉眼验证注入是否生效）。
